Before you press record

Get all of this done before the first take.

Machine setup

  • Install OBS Studio or prepare Loom Set Output to 1920x1080, 30fps, MP4. If OBS will not cooperate, Loom in the browser works.
  • Turn on Focus Assist / Do Not Disturb Mute Windows notifications, Slack, Discord, and anything else that can pop a toast mid-take.
  • Close every window except the browser and terminal Alt-Tab between exactly two windows throughout the recording.
  • Hide the browser bookmarks bar Press Ctrl+Shift+B for a clean browser frame.
  • Set terminal font to 18-20pt with dark theme A judge may watch this on a laptop. The git output and the scorer table have to stay readable.

Audio setup

  • Record in a quiet room with soft furnishings Curtains, rugs, or bedding soak up the room reverb. Turn the fans off.
  • Speak across the microphone at roughly 30cm distance Speaking across it, rather than into it, keeps the p and t sounds from popping.
  • Add Noise Suppression (RNNoise) and Compressor filters in OBS Right-click Mic/Aux, choose Filters, add both. That holds the levels steady.
  • Test audio levels for 10 seconds Speech should peak between -12dB and -6dB and never touch red.

Staged windows

  • Tab 1: groundtrack-console.vercel.app Load the page first and pause the walkthrough autoplay, so you drive the steps yourself.
  • Terminal: open at F:\Projects\ibm-bob-challenge, screen cleared
  • Dry-run the terminal commands once Check that the virtualenv interpreter runs clean and prints the numbers you expect.

Recording workflow

How to get a clean single take.

  1. Read through the script twice with a timer Hold an even pace, around 140 words per minute.
  2. Perform one full rehearsal take with window switches The Alt-Tab switches and the clicks have to land with the narration.
  3. Record the full take If something goes wrong in the first 15 seconds, start over. Past a minute, talk through the small stumbles.
  4. Review the recorded file Check the audio levels, the terminal font size, and that the runtime is under 3:00.

Judge Q&A

Short answers to the technical questions a judge is likely to ask.

Did IBM Bob find the winning parameters, or did you?

An offline search on the development split found the two constants. Bob authored the code and the reasoning, the search supplied the numbers, and the held-out grader judged the result. That split is recorded in the README, in docs/parameter-search.md, and in Bob's own provenance comments inside engine/detect.py. The claim on the table is that Bob authored the engine code, and it has never been that the agent picked the parameters on its own.

Is a held-out split not standard practice in machine learning?

Data splitting is standard in model training. Here the split governs an autonomous coding agent's revisions: Bob generates the code changes and can reach neither the evaluation metric nor the test set. Across 432 parameter configurations, the development and held-out scores showed zero correlation, so tuning against the data the agent can see buys nothing on the data it cannot.

Recall decreased from 25 to 19. Why is this preferable?

On the held-out recordings the engine finds 19 of 35 faults, and false alarms dropped from 128 to 7. For a small team triaging alerts by hand, that takes 121 items out of the queue. The parameters sit as two constants in engine/detect.py, so an operator who needs the recall back can move them with the included search scripts.

How is it verified that code was not edited manually after Bob's runs?

git log --format='%an' -- 'engine/*.py' returns only IBM Bob. git diff 9cc792e -- 'engine/*.py' comes back empty, so nothing has changed since Bob's final commit. The whole repository was checked again from a fresh clone.
